## Summary

The builder is a rectangular, axis-aligned reconstruction template rather than a reconstruction of a connected building topology. It preserves many record IDs but does not necessarily preserve their physical location, boundary, or ownership. Its main roof is always assembled from up to two largest roof records as a two-sided roof along the width axis, regardless of roof type. Additional facets are classified using one side addition and area/pitch heuristics rather than explicit roof ownership. Wall faces share four canonical planes and a common base, so distinct walls can overlap even though none were removed. Attachments do use their supplied dimensions and parent links when usable, but they remain generic boxes and their separately measured roofs and walls are not assembled into a coherent component. Calculation correctly keeps several quantities independent of these guesses, which means a plausible takeoff is not proof of a correct model. Presentation adds unmeasured closure surfaces, translucent secondary-color triangles, and screen-space dimension rails, creating additional visual phenomena distinct from missing measurements. Existing schema fields would eliminate several guesses if used, but the schema still lacks the face-boundary/adjacency/volume topology needed for general reconstruction. A general solution therefore requires a topology contract and explicit uncertainty handling before further visual polish.

## 2. Skip, drop, simplification and visibility ledger

This is the static code-path inventory. It intentionally does **not** invent per-project dropped IDs.

1. **Whole preparation rejected:** nonobject raw input → unreadable; missing/unsupported schema metadata → older-version; normalization/calculation/cards exception → unreadable (P:461–494).
2. **Preparation collection filtering:** malformed collection, nonobject entry, missing required identity/class/type, duplicate ID → removed (P:43–76,215–301). Malformed optional nested values, points, references or warnings → stripped, one generic warning (P:87–199,302–359). A sanitized dimension is not the same as a removed face.
3. **Raw-builder collection filtering:** nonarray collection or nonobject entry → omitted; malformed ID → replaced by generated display ID (B:543–565). Unlike preparation, this does not deduplicate or require class/type. Footprint processing reads raw attachments before `modelParts` sanitizes them (B:330–338,1248–1258); malformed direct-builder input is therefore not guaranteed safe merely because its comment says it is.
4. **Face routing:** only exact `wall` and `roof_face` classes enter detailed construction (B:1248–1250). Other face classes are omitted from detailed geometry, or excluded from per-face display with possible whole-building fallback (B:1500–1513). Fascia and soffit are included in quantities but not detailed 3D.
5. **Walls:** no explicit recognized-wall drop branch in B:1273–1319. Every prepared recognized wall is pushed; overlap, zero height, wrong plane, occlusion and coincident IDs must be diagnosed separately.
6. **Roof simplification:** largest two main, up to two secondary, rest cross facets; all records are bucketed but not physically reconstructed (B:1321–1479). Degenerate span retained (B:595–597). The fallback loop skips an ID already represented, otherwise adds a square plane (B:1483–1494); this is not a general topology solver.
7. **Unsupported whole shape:** non-gable roof type adds only an internal note, while geometry remains the template (B:1496–1498). Its exact phrase “not a supported topology” does not contain the classifier substring “unsupported”; it becomes `general`/`model_note` (B:1164–1192), and neither diagnostic-category handling nor note regexes in W:23–48 expose it as a model UI warning. A flat roof can therefore be wrong with no model UI warning if no other warning-producing path fires. No special hip facet omission is necessary to explain a missing-looking roof slope.
8. **Attachment drop:** detailed proxy heuristic succeeds → omit proxy; width null/nonpositive → omit (B:996–1017). Missing/nonpositive height/depth → width substitution (B:1019–1023). Parentless fallback and generic boxes simplify retained objects (B:1032–1089).
9. **Opening drop/reparent/clamp:** invalid width/height → omit; no discoverable wall/roof parent → omit; invalid parent → guess another; position inference/clamping silently changes shape location with partial notes (B:400–444,893–961).
10. **Conditions:** invalid/nonpositive area → omit; no usable parent → omit; all other shapes replaced by squares with clipped coordinates (B:1103–1140).
11. **Edges:** no match within 20 mm, near-tied distinct candidates, no supported edge class, no matching roof ridge → null then filtered (B:708–781,783–839,1522–1524). Missing length becomes zero before matching and may still be omitted (B:795–796); note “retained as zero-length” does not guarantee final retention.
12. **Downspouts:** preparation and calculation retain/count them, but builder input/model has no downspout collection and buildModel never constructs them (P:295–301; D:300–303,341–345; I:85–103; T:146–169).
13. **Massing substitution:** absent footprint plus faces with no width or height → one first-face area-derived polygon (B:1514–1520,643–666), not all missing faces. Its first-face basis means record order can affect fallback appearance.
14. **Main-bounds exclusion:** max-x filtering only changes main bounds inputs, not output wall/roof arrays (B:1547–1555,1614–1622). Do not count these as dropped model faces.
15. **Closure exclusions:** zero-area projections, nonground attachment proxies and nonselected types are absent from closure source list; internal cell boundaries do not get seams; seam omitted if roof not above wall (C:127–154,292,339,364–376). These remove presentation surfaces, not source IDs.
16. **Rendering state/visibility:** not-ready/WebGL/controls failure stops painter creation (V:564–600); all model meshes are otherwise added (V:627–640). Conditions toggle independently; hidden conditions and condition hits during measuring are excluded from picking (V:641,728–730). Source hit behind closure is rejected; snap targets behind meshes are rejected (V:744–759). These are not builder drops.
17. **Dimensions:** null derived value produces no dimension (B:1596–1611); show-dimensions off/null/empty segments filters labels (O:154–165). Silhouette with fewer than three points aborts overlay placement (V:326–333).
18. **Diagnostic suppression:** duplicate code+ID notes collapse into one diagnostic; notes themselves deduplicate exact strings; UI returns at most three model category warnings (B:1193–1205,1633–1634; W:51–55). Complete reason accounting needs raw notes plus record comparison, not the visible warning alone.

### Required runtime accounting

For each real project, record separate ID sets for **stored → prepared → builder output → drawable nondegenerate → visible from chosen camera**. Compare categories independently (faces, edges, openings, attachments, conditions), and preserve suppressed proxy IDs as “represented by other geometry” rather than ordinary loss only if ownership can actually be demonstrated. Compare each wall polygon plane/bounds and coincident triangles to distinguish retained-but-overlapping walls from dropped walls. Capture preparation warnings, model notes and diagnostics, zero-area triangles, original-parent versus model-parent mismatches, and closure-generated mesh IDs. No dropped-ID list for Leipzig or Braamheide is asserted by this static report.

## 4. Measurement topology gaps and existing-data underuse

Do not attribute all missing geometry to the AI: **unused existing fields** and **fields the contract cannot express** are different.

### Existing information not used as geometric authority

- Ordered main footprint polygon exists, but only extents are consumed (S:117–145; B:301–329).
- Per-elevation eave/ridge and grade offsets plus datum note exist, but builder has only global height fields in input type and uses zero wall bases (S:150–200; I:89–97; B:1266–1271,1310).
- Roof-to-attachment ownership is explicitly available in v1.7, including null meaning main roof, but face input omits it and area ranking substitutes for it (S:524–530; I:19–34; B:1321–1358).
- Exact and rounded roof degrees are available; only snapped rise/12 influences geometry, and can be overridden by global rise (S:532–550; B:567–576).
- Attachment `attached`, `include_in_footprint`, dormer style/pitch and subtype exist, but no geometric branch consumes them (S:340–444; B:983–1089).
- Roof type, soffit depth, face material, roof orientation and party-wall context do not produce corresponding geometry (S:104–115,202–212,481–562; B:1496–1513).
- Measured edge classes/lengths exist but constrain only after-the-fact line matching, not roof/wall construction (S:675–723; B:1522–1524).
- Openings and attachments **do** have usable parent/position support; blanket claims that these are ignored would be wrong (B:897–952,1024–1049).

### Information the present schema does not sufficiently supply

1. **Wall-to-footprint segment identity and local frame:** wall width is described as one footprint segment, but faces do not contain that segment's vertex IDs, start/end coordinates, offset along elevation, or normal. “Front” is not unique for main/annex/recess walls (S:452–562). A sequence of widths and one outline can have multiple valid assignments.
2. **Wall ownership:** v1.7 `parent_attachment_id` is described specifically for roof faces, not attachment walls (S:524–530). Reading it for roofs helps, but does not identify which façade faces belong to the annex. Do not call this a guaranteed existing wall-parent field.
3. **Roof adjacency and plane boundaries:** edge records carry class, length and elevation, not endpoints, adjacent face IDs, volume ID or explicit ridge/valley/hip connectivity (S:675–723). Equal lengths can belong to many places; areas/pitches/type cannot uniquely determine arbitrary roof topology.
4. **Volume graph:** one main outline and overall envelope plus attachment dimensions cannot uniquely define multiple intersecting bodies of differing heights, cross wings or independent roof systems. A component/volume ID with its own footprint, elevation datum, transform and roof membership is required for unambiguous assembly.
5. **Detached placement:** `attached:false` says detached but has no world-relative offset, distance or rotation contract. A parent face local x/y is inadequate to recover a free-standing garage's global placement (S:382–416).
6. **Grade and eave semantics:** four per-elevation offsets do not locate changing grade along a segmented wall, and a prose datum is not an executable coordinate transform (S:161–200). Need per-vertex or per-segment absolute base/eave elevations for sloped/stepped sites. Wall grade-to-eave length must not be confused with global elevation.
7. **Roof type per volume and exceptions:** one building roof type plus attachment roof-face pitch does not define secondary hip/flat/shed/mixed topology, overhangs, parapets, gable apex offsets, valleys or half-hip transition heights.
8. **Attachment geometry semantics:** awning/panel thickness, roof-normal mounting offset, canopy support posts, balcony slab/rail voids, bay polygon shape, round pipe diameter and dormer cutout relationship are not equivalent to three box extents. Some dimensions exist but topology and extrusion direction do not.
9. **Opening placement frame ambiguity:** opening position description says lower-left of elevation while parent_face_id identifies a particular face (S:763–803). For a segmented elevation those origins need an explicit, consistent contract. Roof attachments explicitly use along-eave/up-slope coordinates (S:382–387), requiring deterministic roof U/V orientation independent of arbitrary vertex order.
10. **Uncertainty and constraints:** confidence/source exist for measurement values, but no topological alternatives, constraint priority, tolerance envelope, or machine-readable “cannot locate” reason. A guessed layout must not be indistinguishable from measured placement.

## 5. Recommended general approach and dependencies

These are design recommendations, not implemented fixes.

### A. Define one canonical topology and coordinate contract first

Use a component graph rather than a “main house plus one side garage” template. Each volume should have a stable ID, transform, footprint boundary (including concavity/holes when relevant), base/eave profile, wall segments and roof system. Faces and edges refer to shared vertex/edge IDs and volume ownership. Define world Z datum, orientation, local face U/V, handedness and units explicitly. Preserve measurement evidence and confidence separately from reconstructed geometry.

### B. Reconcile footprint and faces, do not choose one blindly

The footprint supplies spatial boundary connectivity; face records supply identity, width, height, gable profile, color/material and openings. Bind faces to explicit segments where available. Where not available, solve the assignment only if constrained uniquely; equal-length ambiguous matches are not enough. If outline and widths disagree outside measured tolerance, report the conflict and show the chosen low-confidence envelope as a clearly identified approximation, retaining all source records in the side panel. Never duplicate every same-elevation wall at local zero or delete the less-convenient record silently.

### C. Build a connected roof network from constraints

Partition roof records by explicit owner first. Roof type supplies a topology prior, not a replacement for measured face boundaries. Use ridge/hip/valley/eave/rake connectivity and endpoint elevations, per-face slope direction and exact pitch, wall gable profiles and eave profiles to solve intersecting planes. Trim facets at actual intersections and shared boundaries; check every expected boundary for closure, nonzero area, nonself-intersection and consistent normals. Roof facets must not drop below their supporting eave/base profile except where the measurement explicitly defines that geometry. Contradictory constraints cannot always produce an honest closed roof: surface the contradiction and choose a documented simplified envelope instead of claiming a general guarantee from insufficient data.

### D. Attachments require both volume and surface-component families

A general attached **volume** on a known parent frame, at a measured offset, with its own size, walls, materials/openings and roof is the right abstraction for additions/garages/bays. It is insufficient for a thin panel, awning, canopy, balcony, pipe or roof opening. Give those explicit primitive/profile families and mounting/extrusion semantics under a common component interface. Preserve positive measured thickness without display-driven thickening. Detached structures use world transforms. Dormers require a relationship to the host roof and their own roof/cheek topology, not a box sitting on an arbitrary slope.

### E. Degrade explicitly and keep quantities independent

Separate statuses: measured, reconstructed uniquely, approximate, unlocated, invalid and intentionally suppressed duplicate proxy. Do not infer physical side from ID parity. Missing positions may warrant an unplaced-element panel or schematic ghost, not a solid at origin. Missing dimensions must not silently become width-sized cubes. If an envelope is necessary, label it approximate and keep it nonauthoritative for snapping, dimension export and takeoff. Return structured diagnostics containing source ID, field, reason, attempted constraint and fallback—not substring parsing. Preserve all source IDs even if they cannot be placed.

### F. Render authoritative geometry, not an accidental second builder

Use opaque wall/roof materials by default; secondary colors should not imply transparency unless transparency is a real material property. Model material regions independently of triangle ordering. Remove coplanar duplicate surfaces through ownership/topology, not by increasing offsets. Openings should have an explicit decal-versus-hole decision. Presentation closure must be clearly marked as inferred and should not conceal topology validation errors or manufacture authoritative selectable dimensions. Use scale-aware clipping and test oblique/underside views.

### G. Dimension actual features

Dimension named vertices/edges and base-to-eave profiles, including each relevant wall side. Keep a separate main/overall footprint dimension convention. Screen rails may move, but extension lines must point to the actual feature endpoints and retain unambiguous association. A plural segment dimension should not discard all but its first segment. Missing feature geometry should yield an unavailable/approximate dimension rather than an unrelated origin-axis label.

### Suggested dependency order

1. Establish reproducible raw/prepared/model/render evidence and structured loss accounting; retain current fixtures as regression inputs.
2. Agree coordinate/datum, volume ownership and topology schema with measurement/prompt owners; distinguish already-captured unused fields from new requirements.
3. Create a shared canonical geometry/constraint layer with deterministic validation, explicit uncertainty and face/edge IDs.
4. Rebuild footprint-to-wall assignment and grade handling on that layer.
5. Rebuild per-volume roof topology/plane solving and attachment ownership; then component-specific surface/thin/round/dormer geometry.
6. Reconcile quantities and geometry provenance without replacing authentic measured takeoff values with guessed mesh area.
7. Replace presentation-only closure as an accidental topology repair; fix material/depth behavior and attach dimensions to canonical features.
8. Run the full requested synthetic and real-project matrix with ID conservation, area/length residuals, closure/intersection checks, rename/reorder invariance, and multi-angle screenshots. Extend it with rotated plans, equal-length repeated façades, off-center ridges, unequal slopes, left/right mirrored wings, multiple additions and deliberately contradictory data.

## 6. Explicit corrections to tempting but unsupported diagnoses

- “Exactly four walls are built” is false: there are four **placement planes**, but every recognized prepared wall is pushed (B:1273–1314).
- “Ridge follows longest side” is false: ridge is always along footprint width/X (B:1360–1381).
- “Gables are moved to short walls” is false: positive gable height stays on its wall's assigned plane, while roof orientation is independent (B:370–388).
- “Attachments ignore parent and position” is false when the parent resolves (B:1024–1049); failure is incomplete assembly and unsafe fallback.
- “Attachment height comes from story count” and “all thin dimensions have a minimum thickness” are not evidenced: positive measured dimensions are honored in box proxies (B:1015–1023).
- “Garage copies main roof pitch” is too imprecise: shared/misidentified height constraints can override the facet's snapped pitch, and owner/height selection is wrong in principle (B:567–576,1423–1437).
- “Walls are all transparent” is false: base is opaque; secondary-color triangles, glazing and overlays have separate alpha rules (R:81–114).
- “Roof surface reaches ground by design” is not true for ordinary positive-eave main facets; inspect generated closure seams and actual heights first (B:1369–1378; C:282–300).
- “Omission warning proves walls were deleted” is false: broad category mapping includes diagnostics actually categorized as `unsupported`/`ambiguity` and omitted proxy/edge records (W:23–45). The non-gable roof-type note says “not a supported topology,” becomes `general`/`model_note`, and produces no model UI warning by itself (B:1164–1192,1496–1498; W:23–48); other omissions can still trigger the generic warning.
- “Schema-valid means reconstructable” is false: quantities and semantic categories are not sufficient to determine missing topology uniquely (S:452–562,675–723).
